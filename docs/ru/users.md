Пользователь идентифицируется составным ключом: парой из типа мессенджера и идентификатора пользователя внутри этого мессенджера. Тип мессенджера - транспортный токен, а идентификатор пользователя - идентификатор внутри конкретного бэкенда. Стабильная текстовая форма ключа:

```text
<messenger>:<user_id>
```

Примеры:

```text
telegram:123456
kontur-talk:employee-id
web:3c2b4c5d-6e7f-48a9-9c10-111213141516
```

Поддерживаемые токены мессенджеров: `telegram`, `kontur-talk`, `web`, `local-cli`. Ключ не должен содержать пробелы или скобки. `local-cli` - внутренний идентификатор, который считается уже активным и админским для локального администрирования.

## Процесс активации доступа

Активация доступа управляется администратором.

1. Новый пользователь мессенджера или web пытается обратиться к боту.
2. Если пользователя ещё нет в серверном списке пользователей, сервер не выполняет действие, отвечает составным ключом пользователя для передачи администратору и записывает пользователя в список недавних пользователей, ожидающих активации доступа.
3. Администратор открывает [`/pending_access`](usage.md#cmd-pending-access) или раздел админского меню "Пользователи, ожидающие активации доступа".
4. Администратор добавляет пользователя командой [`/add_user`](usage.md#cmd-add-user) `<messenger:id> ...` или через меню.
5. Сервер проверяет пользователя через соответствующий бэкенд, создаёт пользователя в серверном списке, очищает запись pending-access и пытается отправить прямое уведомление с упоминанием [`/start`](usage.md#cmd-start): "Доступ активирован. Теперь можно пользоваться ботом. Отправьте /start, чтобы начать работу с командами."

Для Web-пользователей `/api/authorize` (`sign-without-registration`) или `/api/register` (`log-in-with-registration`) сначала создаёт локальный web-идентификатор пользователя и сессию. Затем web-процесс отправляет на сервер IPC-запрос `authorize_user`, и сервер записывает `web:<uuid>` в список пользователей, ожидающих активации доступа. Пользователь может открыть web-чат, но серверные действия остаются ограниченными до активации доступа для этого `web:<uuid>` администратором. У учётки с локальным логином/паролем логин является только локальными web-учётными данными для восстановления того же сгенерированного идентификатора; он не становится серверной идентичностью. Значение web `provider` остаётся типом учётки (`authorization` или `local-password`) и не является значением `auth_methods`.

Администратор может также создать локального web-пользователя с логином/паролем через [Local CLI](applications.md#booking-resources-cli) `/add_user` без рабочего пароля, если включён `log-in-only` или `log-in-with-registration`. Команда пишет только в SQLite web-процесса и не вызывает `authorize_user`. По напечатанной ссылке `/set-password.html` человек задаёт первый пароль; первый успешный `/api/login` затем записывает пользователя на сервере. `/reset_password` может выдать логин существующему пользователю без логина или сбросить текущий пароль и выдать ссылку `/reset-password.html` для учётки, у которой логин уже есть. `/delete_user` удаляет только локального web-пользователя; серверная учётка `web:<uuid>` не меняется.

Пользователи, ожидающие активации доступа, проходят через ограничитель: счётчик отказанных обращений. Повторные попытки могут привести к чёрному списку - серверному списку заблокированных ключей пользователей:

- Первые обращения получают настроенный ответ "нет доступа".
- Начиная с 3-й попытки в ответ добавляется предупреждение об оставшихся попытках.
- На 10-й попытке пользователь автоматически попадает в чёрный список на 7 дней.
- Список недавних пользователей, ожидающих активации доступа, хранит последние 100 записей и записи за последние 3 дня.

Текст ответа можно изменить командой [`/server_settings`](usage.md#cmd-server-settings); сервер всё равно добавляет строку `Ваш идентификатор: <messenger>:<user_id>`:

```text
/server_settings set access.pending_access_user_reply <text>
```

## Основные поля пользователя

| Поле | Значение |
| --- | --- |
| `messenger` | Бэкенд: `telegram`, `kontur-talk`, `web` или `local-cli`. |
| `userId` | Идентификатор пользователя внутри мессенджера. |
| `userKey` / `userKeyString` | Составной ключ, например `telegram:1234`. |
| `firstName` | Имя для отображения. Перед сохранением обрезаются пробелы по краям. |
| `lastName` | Фамилия для отображения. Перед сохранением обрезаются пробелы по краям. |
| `locale` | Предпочитаемая локаль. Пустое значение использует язык мессенджера, системы или значение по умолчанию. В web-интерфейсе языком мессенджера считается язык браузера (`en` или `ru`). Встроенные пользовательские локали: `en`, `ru`, `ru_stand`. |
| `timezone` | Фиксированное UTC-смещение для отображения и ввода даты/времени. Пустое значение использует часовой пояс сервера. |
| `occupationNotifyMode` | Режим уведомлений о занятости: `all`, `mine`, `off`. `mine` означает только события с участием пользователя. |
| `roleName` | Агрегированная роль: `user`, `admin`, `fixed_admin`. |
| `groups` | Группы, к которым у пользователя есть доступ. Пустая/корневая группа отображается как "Корневая группа (все группы)". |
| `groupRoles` | Роли по группам в форме `group=user` или `group=admin`. |

Значения по умолчанию для нового обычного пользователя:

- Роль: `user`.
- Группа: все минимальные корни администрируемых поддеревьев администратора, который создаёт учётную запись. Для серверного/корневого администратора это корневая группа.
- Локаль: значение по умолчанию.
- Часовой пояс: значение по умолчанию.
- Уведомления о занятости: только события с участием пользователя (`mine`).

## Роли

| Роль | Описание |
| --- | --- |
| `user` | Может использовать обычные команды и меню для ресурсов, видимых по группам. |
| `admin` | Может управлять пользователями, ресурсами, чёрным списком, очередями и уведомлениями внутри администрируемых поддеревьев групп. |
| `fixed_admin` | Серверный фиксированный администратор, активный во время запуска сервера с соответствующим `--admin` или настройкой `admin_ids`. Может управлять серверными настройками и всеми группами. |

`fixed_admin` нельзя назначить обычными командами управления пользователями. Эта роль задаётся только конфигурацией/запуском сервера и не сохраняется как постоянная роль. Если при следующем запуске та же учётная запись больше не указана в `--admin` или `admin_ids`, она загружается как обычный `admin`.

## Группы

Группы - нормализованные пути через `/`:

```text
department
department/team
```

Обратная косая черта заменяется на `/`, пробелы вокруг сегментов удаляются, пустая группа означает корневую группу. Корень покрывает всё дерево и отображается как "Корневая группа (все группы)". Списки групп ресурса в [`/add_resource`](usage.md#cmd-add-resource), [`/update_resource`](usage.md#cmd-update-resource) и мастере ресурсов отклоняют токены с `=` или пустыми сегментами пути (например `office//floor1`).

Группы иерархические. Доступ к родительской группе распространяется на вложенные группы. Например, доступ к `office` покрывает `office/floor1`.

Группы есть и у пользователей, и у ресурсов. Пользователь видит или администрирует ресурс, если его групповые права покрывают группу ресурса.

Если администратор группы не указывает группы при добавлении пользователя или ресурса, объекту
назначаются все минимальные корни его администрируемых поддеревьев. Явно указанные группы заменяют
это значение по умолчанию и могут быть любыми потомками этих корней. Для изменения объекта с
несколькими группами нужны административные права на каждую старую и каждую новую группу, поэтому
администратор не может переместить или удалить объект через родительскую либо соседнюю ветвь.

Записи ожидающих активации пользователей не имеют группы до активации. Глобальный список доступен
только серверным/корневым администраторам; администратор группы всё ещё может активировать известный
`messenger:id`, и при отсутствии явных групп назначаются его администрируемые корни. Глобальными
длительностями занятости также управляют только серверные/корневые администраторы.

Роли по группам задаются списком через запятую:

```text
office=user,office/floor1=admin
```

## Несколько ключей у одного человека

Система не объединяет идентичности из разных мессенджеров. Если у одного физического человека несколько составных пользовательских ключей, каждый ключ является отдельным серверным пользователем:

- `telegram:1234` и `web:...` - разные пользователи.
- Имена могут совпадать, но права, группы, настройки, чёрный список, очередь, расписание и статистика привязаны к ключу.
- Нужно активировать доступ для каждого ключа, которым человек будет пользоваться.
- Если человеку нужен одинаковый доступ в нескольких интерфейсах, роли и группы нужно выдать каждому ключу отдельно.

Это особенно важно для Web: после авторизации пользователь получает `web:<uuid>`. Даже если этот же человек уже имеет доступ в Telegram, для web-идентификатора нужно отдельно активировать доступ, прежде чем web-чат сможет выполнять серверные команды. Локальный логин/пароль может восстановить тот же web-идентификатор, но не объединяет его с идентичностью в другом мессенджере.
